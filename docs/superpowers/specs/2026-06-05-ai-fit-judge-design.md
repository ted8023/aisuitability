# AI 适合度判断器（AI-Fit-Judge）设计文档

**日期：** 2026-06-05
**状态：** 设计已确认，待写实现计划

## 1. 产品概述

用户输入一个问题或项目描述，系统返回一个 **0-100 的「AI 适合度」评分** 加 **一句理由**。
评分越高代表越适合（也越推荐）用 AI 来解决；评分越低代表越不值得用 AI。

**核心目的：** 节省 token，避免把 AI 用错地方——在用户真正调用大模型之前，先用极低（甚至零）成本判断这件事值不值得交给 AI。

### 目标用户
- **普通用户 / 非技术人员**：在用 ChatGPT、Claude 等工具前，判断这个问题值不值得问 AI。
- **企业 / 团队**：在立项阶段判断某个项目是否适合引入 AI，节省资源。

（明确排除开发者：开发者做 vibe coding 时用 AI 几乎总是合适的，且有能力自行兜底，不需要这个判断层。）

### 交付形态
MVP 先做 **Web 应用**验证核心判断逻辑；API / SDK 集成层后续开放。

## 2. 核心设计：单轴评分

系统唯一输出是 **AI 适合度评分（0-100）+ 一句理由**。
不再有独立的「推荐 / 不推荐」标签——是否推荐一切以评分说话，分数越高越推荐。

### 评分语义
- **0 分**：仅当 AI 根本做不了——需要物理动作或真实世界执行。
  例：「帮我订一份外卖」「帮我把空调打开」「帮我去银行取钱」。
- **低分但非 0**：AI 能做，但做得勉强，或有更好的替代方式。
- **高分**：AI 的强项——写作、总结、头脑风暴、翻译、代码、解释概念等。

**重要原则：** 只要 AI 有能力解决，评分就大于 0。性价比低或有风险只会拉低分数，不会归零。

### 影响评分的三个因素（按优先级）
评分不是三个独立结论，而是由以下三个因素共同决定高低：

1. **性价比（优先过滤）** — 有更简单的工具能做到吗？拉低分数。
   - 搜索引擎能直接查到、计算器能算、Excel 能处理、表单工具能收集等。
2. **风险** — AI 在这类问题上容易出错或造成危害吗？拉低分数。
   - 医疗诊断 / 用药、法律判断、需要实时数据、精确财务计算 / 报税等。
3. **问题性质（决定基础分）** — 越是 AI 强项，基础分越高。

### 示例

| 问题 | 评分 | 理由 |
|------|:---:|------|
| 北京今天天气 | 65 | AI 能回答，但搜索引擎更快更省，性价比不高 |
| 1234×5678=? | 60 | AI 能算，但计算器更准更省 |
| 我头痛吃什么药 | 45 | AI 可给参考，但医疗有风险，建议结合就医 |
| 帮我写一封道歉邮件 | 95 | 文字创作是 AI 强项 |
| 帮我订一份外卖 | 0 | AI 无法执行真实世界操作 |

## 3. 整体架构

采用**规则预筛 + 轻量 AI 兜底**的两层架构：

```
用户输入（问题 / 项目描述）
        ↓
  [预处理层] 清洗、分词、提取特征
        ↓
  [第一层：规则引擎]
    ├─ 命中规则 → 直接给出评分 + 理由（跳过 AI，零 token）
    └─ 未命中（模糊）→ 进入第二层
        ↓
  [第二层：Haiku 轻量判断]
    输入：原始问题 + 预处理特征
    输出：结构化 JSON（评分 + 理由）
        ↓
  [结果渲染层]
    - AI 适合度评分（0-100）
    - 理由
    - source 标注（rule / ai，提示本次是否消耗 token）
```

**「过滤」的含义：** 规则层在某维度命中后，**直接定下该问题的评分和理由并跳过 Haiku**，而不是把问题丢弃。所有输入最终都会得到一个评分。预期约 80% 的输入能在规则层解决，不消耗 token。

## 4. 模块拆分与契约

系统拆成 5 个职责单一的模块：

| 模块 | 输入 | 输出 | 依赖 |
|------|------|------|------|
| `preprocess` | 原始文本 | `{cleaned, features}` | 无 |
| `ruleEngine` | features | `{score, reason}` 或 `null`（未命中） | 规则库（配置文件） |
| `aiJudge` | cleaned 文本 | `{score, reason}` | Haiku API |
| `evaluator` | 原始文本 | `{score, reason, source: 'rule' \| 'ai'}` | 上面三个 |
| 前端 | 用户文本 | 渲染评分 + 理由 | evaluator API |

**关键流程：** `evaluator` 先调 `preprocess` → `ruleEngine`；若 `ruleEngine` 返回 `null` 才调 `aiJudge`。`source` 字段让前端能标注本次判断是否消耗了 token，呼应产品省 token 的初衷。

### 数据流图

```
┌─────────────────────────────────────────────────┐
│  1. Web 前端（输入框 + 结果卡片）                   │
└────────────────────┬────────────────────────────┘
                     ↓ HTTP POST /api/evaluate
┌─────────────────────────────────────────────────┐
│  2. 评估编排器 evaluator                           │
│     返回 {score, reason, source}                  │
└──────┬──────────────┬───────────────┬───────────┘
       ↓              ↓               ↓
┌────────────┐ ┌──────────────┐ ┌────────────────┐
│3.preprocess│ │4.ruleEngine  │ │5.aiJudge(Haiku)│
│ 清洗/特征   │ │ 命中→评分     │ │ 评分+理由       │
│            │ │ 未命中→null   │ │                │
└────────────┘ └──────────────┘ └────────────────┘
```

## 5. 规则库（规则引擎内容）

规则库是独立的配置文件（JSON/YAML），与代码解耦，方便持续增删。规则按因素分组，每条规则命中后直接给出建议评分区间与理由模板。

### 性价比类（拉低分，评分非 0）
| 规则 | 示例 | 理由方向 / 替代 |
|------|------|---------|
| 可用搜索引擎直接查到 | 北京今天天气、苹果股价 | 搜索引擎更快更省 |
| 纯数学 / 逻辑计算 | 1234×5678=? | 计算器更准 |
| 结构化数据处理 | 把这 100 行数据排序 | Excel / 表格工具 |
| 字数极短且有唯一确定答案 | 水的沸点 | 搜索引擎 |
| 表单 / 问卷收集 | 收集员工满意度 | 问卷工具 |

### 风险类（拉低分，评分非 0）
| 规则 | 示例 | 理由方向 / 替代 |
|------|------|---------|
| 医疗诊断 / 用药建议 | 我头痛吃什么药 | 有医疗风险，建议就医 |
| 法律判断 / 合同效力 | 这份合同有没有法律漏洞 | 建议咨询律师 |
| 需要实时 / 最新数据 | 今天 A 股开盘情况 | 专业数据源 |
| 精确财务计算 / 报税 | 帮我算今年应缴税额 | 会计 / 税务软件 |

### 不可解类（评分 0）
| 规则 | 示例 | 理由 |
|------|------|------|
| 需要物理动作 / 真实世界执行 | 帮我订外卖、开空调、去取钱 | AI 无法执行真实世界操作 |

### 模糊区
未命中以上任何规则的输入，`ruleEngine` 返回 `null`，由 `aiJudge`（Haiku）综合判断给出评分 + 理由。

## 6. 技术选型（MVP）

- **前端：** 单页 HTML + 原生 JS（或轻量 React），一个输入框 + 结果卡片，不引入重型框架。
- **后端：** Node.js + Express（或 Python + FastAPI），单一 `/api/evaluate` 端点。
- **规则库：** 独立的 JSON/YAML 配置文件，与代码解耦。
- **AI：** Anthropic Haiku（`claude-haiku-4-5`），低成本。

## 7. 错误处理

| 场景 | 处理方式 |
|------|---------|
| 输入为空 / 超长 | 前端拦截，提示用户（超长截断到合理上限） |
| Haiku API 超时 / 失败 | 降级：返回规则引擎保守默认分 + 理由「AI 判断暂不可用，以下为粗略估计」，不让用户卡死 |
| Haiku 返回非结构化 / 解析失败 | 重试一次；仍失败则走降级 |
| 规则库加载失败 | 启动时校验，加载失败则启动报错（fail fast） |

## 8. 测试策略

- `preprocess`：单元测试，验证清洗和特征提取。
- `ruleEngine`：单元测试，每条规则给正例 + 反例（命中 / 不命中）。
- `aiJudge`：用固定 prompt + mock 响应测试 JSON 解析与降级逻辑。
- `evaluator`：集成测试，验证「规则命中不调 AI」「规则未命中才调 AI」的分流逻辑。
- 端到端：几个代表性输入（天气 / 写邮件 / 订外卖 / 医疗）验证全链路评分合理。

## 9. 范围与非目标（YAGNI）

**MVP 范围：** Web 应用 + 单一评估端点 + 两层判断 + 规则库。

**明确不做（后续再议）：**
- API / SDK 对外开放（先验证核心逻辑）。
- 用户账号、历史记录、用量统计。
- 浏览器插件形态。
- 规则库的可视化管理后台。
- 面向开发者的技术问题判断。
